Step 4: Undo Operation using Git (1 Mark)

Demonstrated an undo operation using git reset HEAD~1. An accidental commit was recorded, followed by resetting HEAD to the prior state while safely preserving working tree files.

1. Recording Temporary Commit (To Be Undone):

$ echo "Temporary experimental notes" > experimental.txt
$ git add experimental.txt && git commit -m "Add experimental feature notes (to be undone)"
[main 74b920f] Add experimental feature notes (to be undone)

 create mode 100644 experimental.txt

$ git log -n 2 --oneline
74b920f (HEAD -> main) Add experimental feature notes (to be undone)

2. Executing Undo via git reset HEAD~1:

$ git reset HEAD~1
$ git status
On branch main
Untracked files:
    experimental.txt
nothing added to commit but untracked files present

01c8d6d (HEAD -> main) Add .gitignore to ignore log files and temp directory
a02bbb4 Merge branch 'feature' into main
Effect on Repository State
git reset HEAD~1 successfully undid commit 74b920f by repositioning the HEAD pointer back to 01c8d6d. The commit snapshot was removed from the commit graph while preserving the modified working tree files as untracked, avoiding unwanted data loss.

Question 2: Test Case Design

10 Marks

Application Scenario & Functional Requirements

System Under Test: A Web Login System receiving three interactive user inputs: Username (text input), Password (masked text input), and Login (action trigger button).

Functional Requirements (FR) Specification
  • FR-1: Username must not be empty.
  • FR-2: Password must be at least 6 characters long (length ≥ 6).
  • FR-3: Valid username and password allow a successful login.
  • FR-4: Invalid credentials should display an error message.
  • FR-5: After 3 consecutive failed login attempts, the account should be locked.

Test Design Methodology: Equivalence Partitioning & Boundary Value Analysis

Input Variable Equivalence Classes (Valid & Invalid) Boundary Value Analysis (BVA)
Username • Valid: Non-empty existing username
• Invalid: Empty string ("")
• Invalid: Non-existent username 		• Length = 0 (Empty - Invalid boundary)
• Length = 1 (Single character - Valid minimum)
Password • Valid: Length ≥ 6 characters
• Invalid: Length < 6 characters
• Invalid: Empty string ("")
• Invalid: Incorrect password for valid user 		• Length = 0 (Empty - Invalid)
• Length = 5 (Below minimum - Invalid boundary)
• Length = 6 (Exact minimum threshold - Valid boundary)
• Length = 7 (Above minimum - Valid)
Failed Attempts (FR-5) • Valid range: 0, 1, 2 failed attempts (Account remains Active)
• Critical Threshold: 3 consecutive failed attempts (Triggers Lockout)
• Post-lockout: 4+ attempts (Account locked, login rejected) 		• Attempt 2: Boundary safe (1 attempt remaining)
• Attempt 3: Boundary trigger (Account locks immediately)
• Reset on Success: Successful login resets counter to 0

State Transition Model for Account Lockout (FR-5)

[State 0: Active (0 Failures)]
  └── (Fail 1: Incorrect password) ⟶ [State 1: Active (1 Failure)] — 2 attempts remaining
  └── (Success: Valid credentials) ⟶ [State 0: Active (Counter = 0)] — Dashboard Access

[State 1: Active (1 Failure)]
  └── (Fail 2: Incorrect password) ⟶ [State 2: Active (2 Failures)] — 1 attempt remaining
  └── (Success: Valid credentials) ⟶ [State 0: Active (Counter reset)] — Dashboard Access

[State 2: Active (2 Failures)]
  └── (Fail 3: Incorrect password) ⟶ [State 3: LOCKED (Lockout Triggered)] — Logins Blocked
  └── (Success: Valid credentials) ⟶ [State 0: Active (Counter reset)] — Dashboard Access

[State 3: LOCKED]
  └── (Any Attempt: Valid or Invalid) ⟶ [REJECTED: "Account is locked" message]
